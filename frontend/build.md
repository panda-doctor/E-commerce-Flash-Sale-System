# Codex AI Agent 自主开发任务：基于现有后端工程完成前端业务模块开发

## 一、角色与任务目标

你是一名资深全栈工程师、前端架构师和 AI Coding Agent，具备独立分析代码库、理解业务需求、设计前端架构、编写代码、调试接口、运行测试和修复问题的能力。

当前项目采用前后端分离架构。后端已经存在实际的业务代码和 API 接口，我需要你以**现有后端工程的真实代码作为业务依据，自主完成前端对应业务模块的分析、开发、集成、调试和验证**。

前端技术栈原则上采用：

- React
- TypeScript
- Vite
- React Router
- Axios 或项目中已有的 HTTP 请求方案
- 项目现有的 UI 组件库、状态管理方案和样式系统

如果现有前端工程已经采用其他兼容的依赖、架构或规范，优先沿用现有方案，不要为了使用上述技术而破坏已有工程。

本次任务不是编写开发方案，也不是只生成示例代码。你必须直接操作当前工作区中的工程，完成实际代码修改，并尽可能运行、构建、测试和修复。

**核心原则：先理解后端，再设计前端；先确认真实接口，再编写调用代码；先完成业务闭环，再进行质量优化。**

## 二、AI Agent 自主执行规则

你需要按照自主开发 Agent 的工作模式执行以下任务。

### 1. 自主探索工程

首先检查当前工作区的目录结构，自动识别：

- 后端工程所在目录。
- 前端工程所在目录。
- 项目的技术栈和依赖版本。
- 后端启动入口及配置文件。
- 前端启动入口、路由、页面、组件和请求封装。
- 数据库实体、业务模型、接口 DTO 和统一响应结构。
- API 文档、Swagger/OpenAPI 配置、测试用例及其他辅助文档。

工程可能是单体仓库，也可能是前后端分离的多个子目录。你需要根据现有文件结构自行判断。

不要默认某个目录一定是前端或后端。通过 `package.json`、`pom.xml`、`build.gradle`、源码目录等实际文件确认。

如果当前工作区存在多个工程，优先分析与当前业务相关的工程，并识别它们之间的调用关系。

### 2. 自主阅读和分析后端代码

不要只看 Controller 的接口声明。需要沿着实际业务调用链阅读代码：

`Controller → Service → Repository / Mapper / DAO → Entity / 数据库`

同时检查：

- Request DTO、Response DTO、VO 和参数校验。
- 登录认证、Token 生成与解析。
- Spring Security、拦截器、过滤器或其他权限控制机制。
- 全局异常处理和统一响应封装。
- 分页查询、状态枚举、业务异常及错误码。
- 订单处理、异步任务、消息队列或轮询状态查询等机制。
- 跨域配置、文件上传和业务配置。
- 现有 API 文档、集成测试和单元测试。

如果后端使用的不是 Spring 技术栈，则根据实际框架采取对应的分析方式。

对于每一个需要实现的业务模块，都要明确以下信息：

1. 对应的后端接口是什么。
2. 请求方式、URL、请求参数及请求体是什么。
3. 返回数据结构是什么。
4. 哪些接口需要登录。
5. 哪些操作存在角色权限或其他业务限制。
6. 后端如何处理业务状态和异常。
7. 前端如何将接口响应映射为页面状态。
8. 页面上的操作最终会触发哪些后端业务逻辑。

优先依据可运行的后端代码和实际接口契约判断。不要仅凭方法名称或注释推断业务行为。

### 3. 自主决策并持续执行

你可以自主决定合理的组件划分、目录结构、接口适配方式、状态管理方式、错误处理方案和测试策略。

不要遇到一般性的技术决策就暂停并向我询问。

如果发现信息不完整：

- 先检查源码、配置文件、文档和测试。
- 尝试通过已有的开发环境验证接口行为。
- 根据已确认的后端契约实现能够确定的部分。
- 如果确实缺少必要的后端能力，明确记录缺失项，不得伪造接口或假装功能已经打通。

在安全且可逆的范围内，自主推进开发，不要只停留在分析或计划阶段。

## 三、阶段一：建立后端业务地图

在开始大量编写前端代码之前，先对现有后端进行系统分析。

### 1. 提取真实 API 契约

根据实际源码，整理需要前端使用的 API，至少包含：

| 分析项目   | 必须确认的内容                         |
| ------ | ------------------------------- |
| 接口标识   | 业务名称及用途                         |
| 请求方式   | GET、POST、PUT、PATCH、DELETE 等实际方法 |
| 请求地址   | 完整路径及路径参数                       |
| 参数定义   | Query、Path、Body、Header          |
| 数据类型   | 字段名称、类型、必填规则                    |
| 返回结构   | 实际响应字段与嵌套关系                     |
| 认证要求   | 是否需要 Token 或登录状态                |
| 业务规则   | 状态限制、权限限制、业务校验                  |
| 错误处理   | HTTP 状态、业务错误码和错误信息              |
| 前端使用位置 | 对应页面、组件或业务流程                    |

重点核实后端是否存在统一响应包装，例如 `code`、`message`、`data`，以及分页数据的真实字段。

不要将不同接口的响应结构想当然地统一。应当根据实际接口契约，在前端 API 适配层进行必要处理。

如果工程包含 Swagger/OpenAPI 文档，可以利用它辅助分析，但仍要检查关键业务接口对应的实现代码。

### 2. 绘制业务调用关系

根据实际代码梳理：

- 核心业务模块。
- 模块之间的依赖关系。
- 用户从页面操作到后端业务处理的完整路径。
- 登录状态和权限对操作的影响。
- 后端处理成功、失败、处理中和异常等不同结果的处理方式。

建议形成一份 `docs/frontend-backend-mapping.md`，记录实际确认的业务模块、接口映射和待解决问题。

该文档必须来源于真实代码，不得为了填满文档而虚构信息。

完成分析后，立即进入开发阶段，不要仅提交这份文档就结束任务。

## 四、阶段二：分析现有前端工程

在开始修改代码前，先确认前端当前的实际情况：

1. 是否已经存在页面、组件、路由和公共布局。
2. 是否已经存在 Axios 实例或请求封装。
3. 是否已有登录、注册、Token 存储及退出登录逻辑。
4. 是否已有 API 类型定义、公共响应类型或状态管理。
5. 是否已有组件库、设计规范、主题变量和响应式布局。
6. 是否已有可以复用的业务组件。
7. 当前工程是否存在编译错误、依赖缺失和明显的运行问题。

遵守以下规则：

- 尽可能在现有架构上增量开发。
- 优先复用能够满足需求的组件和工具。
- 不要随意重写整个前端工程。
- 不要随意替换状态管理库、UI 组件库或路由方案。
- 不要重复创建同类的 Axios 实例、Token 管理器和业务 API。
- 不要为了实现一个小功能引入大量新依赖。
- 修改公共组件时，要评估其对现有页面的影响。

如果前端几乎是空白工程，再根据实际后端接口建立合理的基础架构。

## 五、阶段三：前后端 API 对接

建立统一且可维护的 API 调用体系。

### 1. 请求基础设施

根据后端实际配置实现：

- 统一的 API Base URL 配置。
- 统一的 HTTP 请求实例。
- 合适的请求超时策略。
- 请求参数和响应数据的类型定义。
- Token 注入机制。
- HTTP 错误处理。
- 业务错误处理。
- 网络异常处理。
- 登录状态失效处理。
- 必要的请求取消及重复请求控制。

开发环境下的 API 地址优先通过 Vite 环境变量配置，例如：

`VITE_API_BASE_URL`

如果项目已有其他环境变量命名方式，则沿用现有约定。

检查现有跨域配置。如果开发环境适合通过 Vite 代理解决跨域问题，可以配置开发代理，但不得将其错误地当作生产环境跨域配置已经解决的依据。

### 2. 类型安全

使用 TypeScript 为核心接口建立准确的类型定义，包括：

- 请求参数。
- 请求体。
- 响应对象。
- 分页数据。
- 业务状态枚举。
- 用户信息。
- 商品和活动信息。
- 订单和异步处理结果。

字段必须来自后端实际定义。

对于后端中可能存在的空值、缺失字段和可选字段，使用准确的类型表示，不要为了消除类型错误而滥用 `any`、类型断言或非空断言。

如果后端字段和前端展示模型不同，在 API 适配层完成显式转换。

### 3. API 使用规则

所有实际业务调用必须经过统一的 API 模块。

页面和组件原则上不应直接散落请求 URL、重复拼装 Token 或各自处理相同的业务响应格式。

必须遵循以下原则：

- 不允许凭空编造后端接口。
- 不允许为了让页面显示成功而伪造成功响应。
- 不允许用本地硬编码数据冒充真实后端业务结果。
- 不允许忽略后端响应中的失败状态。
- 不允许在前后端数据结构不一致时静默吞掉错误。
- 不允许用静态 JSON 替代本应由真实后端提供的数据。

本地模拟数据只能用于明确标识的开发预览或测试场景，不能作为已完成真实 API 对接的证明。

## 六、阶段四：根据真实业务开发前端模块

请根据后端实际提供的业务能力，建立完整的前端业务页面和用户操作流程。

本项目的目标业务是商品秒杀商城。优先实现以下模块；如果某个模块的后端能力不存在，则记录缺失的接口或业务能力，不得自行假设它已经实现。

### 模块 A：商品首页与商品列表

需要实现：

- 商品列表展示。
- 关键词搜索。
- 商品或秒杀活动状态筛选。
- 分页查询。
- 商品详情入口。
- 商品图片展示与异常兜底。
- 加载状态、空数据状态和失败重试。
- 在合适的生命周期内刷新活动数据。

商品卡片优先展示后端真实返回的内容，例如：

- 商品名称。
- 商品图片。
- 商品描述或摘要。
- 原价、活动价。
- 活动开始与结束时间。
- 当前活动状态。
- 剩余库存。
- 进入详情页或参与秒杀的操作入口。

具体显示哪些字段，以真实业务模型为准。

图片 URL 缺失或加载失败时，展示清晰的“暂无商品图”占位状态，避免破图图标和影响布局的异常。

分页、搜索和筛选必须真正影响后端查询结果。切换筛选条件后，要合理重置页码并处理并发请求，避免旧请求的返回结果覆盖新条件下的数据。

定时刷新应考虑页面是否仍然可见、组件是否已卸载、是否存在重复请求等问题，避免无意义的持续请求。

### 模块 B：商品详情与秒杀活动

需要实现：

- 商品基础信息与详情展示。
- 活动价格与原价展示。
- 活动开始和结束时间。
- 活动状态。
- 当前库存或剩余库存。
- 登录状态判断。
- 参与资格和业务错误提示。
- 秒杀请求提交。
- 异步订单或请求处理状态跟踪。
- 最终业务结果展示。

活动状态和用户可参与条件应尽量以实际后端业务规则为准。前端的时间判断只能用于交互提示，不能作为安全校验依据。

秒杀提交必须调用真实后端业务接口。

提交后，应根据实际后端的处理机制决定后续流程：

- 如果接口同步返回最终结果，则直接处理实际响应。
- 如果接口返回任务 ID、请求 ID、订单 ID 或处理中状态，则通过真实存在的查询接口追踪处理进度。
- 如果后端采用其他消息推送或异步机制，则根据实际架构对接。

对于轮询，需要设置合理的轮询间隔、最大次数或超时时间，并在页面卸载、请求完成或任务明确结束后停止轮询。避免无限轮询和多个重复轮询任务。

只有后端确认成功时，才显示秒杀成功或订单成功。对于库存不足、活动尚未开始、活动结束、重复参与、资格不符、系统繁忙等情况，按照真实后端错误码或业务响应进行处理。

不要仅依靠前端按钮禁用来防止重复请求。前端可以做交互层面的重复提交控制，但真正的业务约束必须遵循后端实现。

### 模块 C：注册、登录与账户管理

根据后端实际接口实现：

- 用户注册。
- 用户登录。
- 退出登录。
- 当前登录状态维护。
- 用户昵称或基本资料展示。
- 登录失败反馈。
- Token 过期或失效处理。
- 未登录访问受保护页面时的处理。
- 需要登录的操作拦截。

必须检查后端实际采用的认证方式，包括 Token 类型、Header 名称、前缀规则、过期策略，以及是否采用 Cookie 或其他机制。

不要擅自假设认证方案一定是 JWT Bearer Token。

不要将密码、Token、密钥等敏感数据输出到控制台日志或错误提示中。

Token 的存储方式应依据后端认证设计和项目的安全要求选择，不要无条件将敏感凭据保存在 `localStorage`。如果项目采用 Cookie 认证，必须考虑凭据发送和相应的 CSRF 防护策略。

注册和登录表单需要具备基础校验、提交状态、重复提交保护、可读的错误信息及合理的成功反馈。

### 模块 D：我的订单

根据真实订单接口实现：

- 当前用户的秒杀订单列表。
- 订单分页或其他后端实际支持的查询条件。
- 订单状态展示。
- 订单详情或可用的订单操作入口。
- 处理中订单的状态刷新。
- 加载中、空订单、请求失败等状态。

订单状态文案必须由真实后端状态枚举映射得到，不得随意定义与后端不一致的状态。

如果存在多个订单生命周期阶段，应当在前端统一管理状态映射，不要在多个组件中重复书写分散的字符串判断。

仅允许用户查看和操作符合后端权限规则的数据，不要通过前端隐藏按钮来代替后端授权。

### 模块 E：其他真实业务模块

除上述模块外，还需要主动发现后端实际提供的其他用户端业务能力。

如果后端存在个人中心、用户资料修改、地址管理、分类浏览、订单详情或其他明确属于本前端的能力，应结合现有工程判断是否需要实现。

对于后台管理接口、内部运维接口或不属于当前前端范围的模块，不要未经判断就全部开放到用户端。

优先完成核心业务闭环，再实现其他必要模块。

## 七、阶段五：UI 与交互质量

整体视觉延续主流电商平台风格：**明亮、简洁、可信、突出促销信息，同时保持统一的布局和清晰的信息层级。**

### 视觉规范

- 采用白色或浅灰色为主的页面背景。
- 使用清晰的主色与促销强调色。
- 商品价格、秒杀按钮、限时活动等重要信息需要突出显示。
- 合理使用留白、圆角、轻量阴影和细分隔线。
- 避免大面积高饱和色块和过多渐变。
- 商品卡片、详情页、表单和订单列表使用统一的视觉规范。
- 使用清晰的字体层级、间距体系与图标风格。
- 根据桌面端与移动端尺寸适配页面布局。
- 不要因过度追求视觉效果而降低信息可读性。

### 交互规范

重要页面应至少具备以下真实界面状态：

1. 初始加载状态。
2. 正常数据状态。
3. 空数据状态。
4. 接口错误状态。
5. 提交中状态。
6. 操作成功状态。
7. 操作失败状态。
8. 未登录或无权限状态。

按钮必须与真实业务行为对应。无后端能力的功能不能伪装成可正常使用的功能。

对表单、弹窗、分页、筛选、导航和状态切换进行实际检查，避免只有视觉效果而没有有效的交互逻辑。

## 八、阶段六：代码质量与架构约束

请结合现有工程情况，采用清晰、可维护的模块划分。

在必要时，可参考以下组织方式：

- `src/api/`：业务 API 调用。
- `src/types/`：接口和业务类型。
- `src/pages/`：路由页面。
- `src/components/`：可复用 UI 组件。
- `src/hooks/`：可复用业务 Hooks。
- `src/router/`：路由配置。
- `src/utils/`：通用工具。
- `src/stores/`：全局状态管理。
- `src/styles/`：全局样式与主题变量。

以上目录仅供参考，应根据现有项目结构进行调整，不要机械地重复创建目录。

必须遵守：

- 使用 TypeScript 和清晰的类型定义。
- 将网络请求与页面展示逻辑合理分离。
- 避免巨型组件和重复业务代码。
- 避免不必要的全局状态。
- 对异步操作进行完整的成功和失败处理。
- 正确清理定时器、轮询和事件监听。
- 避免组件卸载后的无效状态更新。
- 避免 React `key`、依赖数组和闭包使用方面的常见错误。
- 避免过度使用 `useEffect`、不必要的重新渲染和重复请求。
- 遵守现有 ESLint、Prettier 和 TypeScript 规范。
- 删除确实不再需要的临时调试代码。
- 不要通过关闭类型检查、屏蔽 ESLint 或删除测试来规避问题。

如果需要新增依赖，先检查现有依赖是否已能够实现需求，并选择必要且兼容的方案。

## 九、阶段七：自主运行、联调和修复

代码编写完成后，必须主动验证，而不是以文件生成成功作为完成标准。

### 1. 静态验证

检查：

- TypeScript 类型错误。
- ESLint 错误。
- 组件导入与导出错误。
- 路由配置错误。
- API 参数和返回类型不一致。
- 环境变量读取错误。
- 轮询、定时器和异步请求清理问题。
- 浏览器端可能存在的运行时异常。

### 2. 构建与测试

优先使用项目已经配置的脚本，检查 `package.json` 中实际存在的命令。

根据项目已有能力运行：

- TypeScript 检查。
- ESLint 检查。
- 单元测试。
- 前端生产构建。
- 必要的集成测试或端到端测试。

如果工程没有某项测试能力，不得声称已经通过该项测试。

### 3. 前后端联调

在可用环境允许的情况下，检查：

- 前端能否正常启动。
- 后端接口能否正常访问。
- Base URL 和代理配置是否正确。
- 登录后是否能够调用受保护接口。
- 数据字段是否正确映射。
- 请求失败是否有合理反馈。
- 分页、搜索、详情和订单查询是否符合实际接口行为。
- 秒杀请求和异步订单处理能否形成完整业务闭环。

不要将 HTTP 请求返回 200 直接视为业务成功，还必须检查实际业务响应。

如果后端服务无法启动、数据库不可用、缺少必要环境变量或测试账号，先完成静态检查和能够独立完成的验证；明确记录受阻项，不要虚构联调结果。

### 4. 主动修复

发现问题后，优先检查原因并直接修复。

修复后重新执行相关检查，直到问题解决，或者遇到无法由前端单方面解决的明确阻塞条件。

不要在没有尝试定位和修复的情况下，将普通 TypeScript 错误、明显的接口适配错误或可解决的构建错误直接交给我处理。

## 十、修改保护与安全边界

自主开发不等于不受约束地修改整个仓库。

必须遵守以下边界：

1. 默认只修改完成前端业务所必需的文件。
2. 不擅自删除或重写已有业务模块。
3. 不随意修改数据库结构、生产配置或后端业务逻辑。
4. 不删除用户原有代码、未提交变更或其他开发成果。
5. 不覆盖现有 `.env`、密钥、证书或敏感配置文件。
6. 不将真实密钥、Token、密码或数据库凭据写入前端源码。
7. 不通过修改后端权限或关闭安全校验使前端功能看似成功。
8. 不擅自执行数据库清空、数据迁移、重置环境、强制覆盖或其他具有破坏性的操作。
9. 不在未检查现有工作区状态前执行可能覆盖用户修改的命令。
10. 不把仅在前端隐藏的权限入口当作权限控制。

如果发现必须修改后端才能完成某项业务，先分析原因。优先在不改变后端行为的情况下完成兼容；如果确实必须修改，则将其与前端修改分开，确认不会破坏现有契约后，再进行最小范围、可验证的修改，并在最终报告中单独说明。
