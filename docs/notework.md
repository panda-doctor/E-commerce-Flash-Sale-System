什么是并发断言？

在软件开发（尤其是电商秒杀、抢购系统）中，并发断言并不是 Java 标准库里的某个特定方法，而是指在多线程/高并发场景下，用于验证系统数据一致性、安全性和业务规则是否被破坏的检验手段。

通俗地说：普通断言是检查“结果对不对”；并发断言是检查“在万人抢购时，结果依然对不对，有没有超卖、多扣、重复下单”。

针对你的“电商秒杀系统”，并发断言主要用来验证以下 4 个核心维度：

1. 数据一致性断言（防止超卖）
这是秒杀最核心的底线。在压测工具（如 JMeter）发起 1000 个并发请求后，你需要断言数据库最终的数据状态：

断言逻辑：最终扣减后的库存 >= 0（绝对不能为负数）。

断言总量：已生成的订单数量 == 初始库存 - 剩余库存。
如果你的 Redis 预扣减和 MySQL 最终落库不一致，普通单元测试测不出来，但并发断言能立刻抓到负数。

2. 幂等性断言（防止重复下单）
断言同一个用户在同一场秒杀中，是否只生成了一个有效订单。

断言逻辑：并发执行 10 次下单请求（携带相同 UserId + ProductId），最终查询数据库，count(orders) == 1。
如果漏掉了分布式锁或防重表，并发断言会发现数据库里插入了多条重复订单。

3. 限流与熔断断言（系统自我保护）
断言在流量超过系统阈值时，系统是否有正确的“拒绝”行为。

断言逻辑：发送 10000 个并发请求，系统返回 HTTP 429（Too Many Requests）或 503 的比例是否符合预期，而不是把所有请求都放过去把服务器打崩。

4. 缓存与 DB 的一致性断言
在更新缓存（Redis）的同时修改数据库（MySQL），断言两者数据在并发下是否最终一致。

在实际项目中，如何落地“并发断言”？
你不能在 main 方法里用 System.out.println 去肉眼盯，因为并发太快了。生产环境中通常使用 压力测试工具 + 脚本断言：

方式	适用场景	实现示例
JMeter 响应断言	接口功能验证	检查返回的 JSON 中 code 是否为 200，msg 是否含“库存不足”
JMeter + BeanShell/JSR223 断言	复杂业务逻辑	在压测脚本中编写 Groovy 代码，请求结束后查询数据库核对库存变化逻辑
测试代码单元并发模拟	开发自测	使用 CountDownLatch + CyclicBarrier + ExecutorService 模拟瞬间并发，并在所有线程结束后用 Assertions.assertEquals() 核对数据库记录数
数据库前置与后置校验	最终一致性检查	压测前记录 Redis 和 MySQL 的库存快照，压测结束后自动比对 初始库存 - 总成功订单数 == 当前剩余库存
