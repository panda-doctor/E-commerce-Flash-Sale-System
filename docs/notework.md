## 一、并发断言：什么是？

在软件开发（尤其是电商秒杀、抢购系统）中，并发断言并不是 Java 标准库里的某个特定方法，而是指在多线程/高并发场景下，用于验证系统数据一致性、安全性和业务规则是否被破坏的检验手段。

通俗地说：普通断言是检查“结果对不对”；并发断言是检查“在万人抢购时，结果依然对不对，有没有超卖、多扣、重复下单”。

针对秒杀系统，并发断言主要验证 4 个核心维度：

1. **数据一致性断言（防止超卖）**：最终扣减后的库存 ≥ 0（绝对不能为负）；`订单总数 == 初始库存 - 剩余库存`。Redis 预扣减与 MySQL 最终落库若不一致，普通单测测不出来，并发断言能立刻抓到负数。
2. **幂等性断言（防止重复下单）**：同一用户同一场秒杀，最终 `count(orders) == 1`。
3. **限流与熔断断言（自我保护）**：流量超阈值时，系统按预期「拒绝」（如 HTTP 429 / 业务码 42900），而不是全放行把服务器打崩。
4. **缓存与 DB 一致性断言**：更新缓存（Redis）与修改库（MySQL）并发下最终一致。

**落地方式**（不能肉眼盯）：
- JMeter 响应断言（检查 `code`）、JSR223/Groovy 断言（压测中查库核对库存）；
- 测试代码里 `CountDownLatch + ExecutorService` 模拟瞬间并发，结束后 `Assertions.assertEquals()` 核对；
- 压测前后对比 `初始库存 - 总成功订单数 == 当前剩余库存`。

> 本项目对应：`SeckillExecuteConcurrencyTest`（200 并发抢 100）、`SeckillUserDedupTest`（同用户 50 并发仅 1 成功）、JMeter 5000 并发（`docs/load-test-report.md`）。

## 二、为什么 Lua 脚本是原子的？

Redis 是**单线程**处理命令的。一个 Lua 脚本从开始执行到结束，中间不会有别的命令插入——所以「读库存 → 判断 → 扣减」这三步放进一个脚本，就等于把竞态窗口整个关掉了。

**什么时候该把多条命令合并进一个脚本？**
- 当这几条命令的**中间状态不允许被别的请求看到**时。秒杀的「建令牌 → 检查库存 → 扣减 → 售罄回滚」必须在同一脚本里——否则网络中断/进程崩溃会留下"令牌建了库存没扣"或"库存扣了没建令牌"的中间态。
- 判断标准：这几步是不是一个**不可分割的业务动作**。

**返回值契约要在脚本头注释写清楚**：`seckill_execute.lua` 返回 `>=0` 剩余库存 / `-1` 售罄（已回滚令牌）/ `-2` 重复秒杀，Java 侧每个码都要映射业务分支，缺一个就会掉进兜底变成 500。

**坑**：
- 脚本参数传数值别传字符串：`String.valueOf(1800)` 经序列化器会带引号 `"1800"`，Lua `tonumber` 得到 nil。
- 拼写：`false` 别手滑成 `flase`（未定义变量，条件恒假成死代码）。

## 三、缓存三兄弟：穿透 / 击穿 / 雪崩

| 名字 | 一句话 | 为什么可怕 | 本项目解法 |
|---|---|---|---|
| 穿透 | 查**不存在的 key** | 每次都绕过缓存打库，恶意用一个随机 id 就能打爆 DB | 查库未命中写**空值标记**（TTL 60s），命中标记直接返回不再打库 |
| 击穿 | 热点 key **刚好过期**的瞬间 | 大量并发同时回源，DB 被瞬时压垮 | Redisson 互斥锁 + **锁内双重检查**（等锁期间别人可能已回源，拿到锁先重查缓存） |
| 雪崩 | 大量 key **同时过期** | 同一时刻集体回源 | 过期时间加随机抖动（300 + random(60)s），错峰失效 |

**坑（本项目反复踩）**：
- 空值标记是 `String ""`，读到它要返回 null **且不能删**；旧的「读到非 Product 类型就删」分支会让空值一读即删、防护失效。
- 锁键要进常量类；`tryLock` 的 wait（防无限等待）与 lease（防持锁崩溃死锁）两个参数都要设；释放前用 `isHeldByCurrentThread()` 判断，防止误释放他人锁。

## 四、幂等四道闸与「售罄回滚」的语义

同一用户一场秒杀只能成功一单，靠**四层闸门**逐级兜底，任一失效下一层还能挡住：

1. **Redis 令牌**：`SET NX EX`（`seckill:user:{activityId}:{userId}`，TTL 30min）——第一道，拦 99.99% 的重复。
2. **DB 唯一键**：`uk_activity_user`——Redis 层漏了，数据库唯一约束兜底，`DuplicateKeyException` 当作"已处理"。
3. **Stream XACK**：消息 ACK 前留在 PEL，进程崩溃能重读不丢（防"重投=重复单"靠上面两道的幂等）。
4. **订单号唯一键**：`uk_order_no`——连订单号都不能重复（曾因双时钟源碰撞丢单，见 load-test-report 3.1）。

**关键语义：售罄要回滚令牌**。令牌是"抢到了"的凭证，若建了令牌却库存不足，不删令牌 = 这个用户没抢到却被锁 30 分钟，语义与体验都错。所以「失败回滚」和「扣减」必须在同一个 Lua 里同生共死（见 seckill_execute.lua）。

**谁的判断才算"抢到了"**：令牌只是排队资格，**以订单最终落库为准**；这也是排行榜只在消费者落库成功侧 `recordSuccess`、而不是 execute 返回就入榜的原因。

## 五、Redis Stream 消费者组的可靠性从哪来

- **消费者组（consumer group）**：同一组内多个消费者分工读同一条 Stream，消息不重复分给同组两个消费者。
- **PEL（Pending Entries List）**：`XREADGROUP` 读到的消息在 ACK 前都记在 PEL。**进程崩溃 → 消息还在 PEL → 重启可用 `XREADGROUP ... 0` 重新读**——这就是"宕机不丢消息"的机制基础。
- **XACK**：处理成功才 `XACK`，把消息移出 PEL。
- **重试 / 死信**：失败不 ACK 留 PEL = 可重试；超过 `MESSAGE_MAX_RETRY`(3) 次，投到死信流 `seckill:order:dead:stream` 并 XACK（不积压主流），由人工回放（`DeadLetterReplayService`）。毒消息（解析都失败）也必须走失败计数，否则永远留在 PEL 空转。

**坑**：
- 用 `ObjectRecord` 投递 bean，读回来字段会变 **Base64 字符串**（`200`→`"MjAw"`）——统一用**明文 Map** 投递，消费端安全转换。
- `XGROUP CREATE` 遇 BUSYGROUP 要幂等：真实异常在 cause 链里（lettuce 包成 RedisSystemException），别只看 `getMessage()`。
- Redis 容器重启即丢数据（无持久化），所以消费者组的创建必须每次启动都做且幂等。

## 六、滑动窗口限流 vs 固定窗口

- **固定窗口**：计数器按整分钟/整小时清零。边界突刺：第 59 秒和第 61 秒各放 5 个请求，跨窗口实际 10 个——绕过了"每分钟 5 次"的约束。
- **滑动窗口（ZSet）**：把每个请求的时间戳存进 ZSet，统计时 `ZREMRANGEBYSCORE` 只保留"当前时刻往前一个窗口"内的成员，再 `ZCARD`。任何时刻往前看一个窗口，永远精确。

**本项目的两个细节**：
- member 必须唯一（`时间戳-随机数`）：只存时间戳的话同一秒两个请求 member 相同，`ZADD` 会把前一个覆盖掉，计数丢失。
- 每次放行 `EXPIRE` 刷新：活跃用户键不提前淘汰；不活跃的键到点自动消失，不需要手动清理。
- 限流键粒度 `activityId:userId` 双维（E4）：单维 `userId` 会让用户在多活动间连点互相误伤。

## 七、分布式锁：什么时候才需要它

**判断标准**：这个操作是不是「单命令/单脚本可原子」？
- **不是**（多步读改写）→ 需要锁串行化。例：预热（查状态→写缓存→更新 DB 状态）、库存重置。用 Redisson `tryLock(wait, lease)`，等锁期间别人可能已完成，拿到锁要**双重检查**，`finally` + `isHeldByCurrentThread` 释放，捕获中断要恢复中断位。
- **是**（单命令可原子）→ 加锁反而是负担。秒杀 execute 的防重+扣减已被一个 Lua 脚本原子完成，主链加锁只降并发，所以锁只护写入口、不护 execute。

**锁与 Redis 事务/Lua 的区别**：锁解决的是"多步操作的整体串行化"；Lua 解决的是"单次操作内的原子性"。本项目两处都用到了，各司其职。

## 八、Redis 序列化与类型（最容易踩的隐藏坑）

- **LocalDateTime 必须注册 `JavaTimeModule`**：`RedisSerializer.json()` 的 ObjectMapper 默认不含时间模块，序列化实体里的 `LocalDateTime` 会报错；用 Spring Boot 的 `ObjectMapper`（已含）`copy()` 后再配序列化器。
- **必须开 DefaultTyping（`@class`）**：否则反序列化无法还原具体类型，`instanceof Product` 会失效。
- **开了 `@class` 就要防反序列化攻击**：DefaultTyping 会按 JSON 里的 `@class` 字段实例化类，若 Redis 数据被污染，`LaissezFaireSubTypeValidator`（放任一切类型）可能被引导实例化任意 gadget。S2 加固改成 `BasicPolymorphicTypeValidator` **白名单**：只放行本工程实体包 + 常用 JDK 类型（`java.time./util./lang./math./net.`）。
- **数值装箱可能在序列化往返后变化**：Long `9900` 存进 Redis 再取出可能变 Integer。断言要 `isEqualTo(9900)` 而不是 `9900L`，先想清楚实际取出类型。
- **实体加字段 → 旧缓存可能反序列化失败**：改动序列化对象的类结构后，老缓存数据可能读不了，开发期 flushdb 或对键设短 TTL。

## 九、工程与环境的坑（遇事不决先看这里）

- Redis 用 `database: 1`，redis-cli 默认连 db0——`redis-cli -n 1` 才看得到键，用错库会误判"键不存在"。
- `keys("seckill:stock:")` 匹配不到 `seckill:stock:100`，要带通配符 `keys("seckill:stock:*")`；且要 `!isEmpty()` 才删，判空写反会永远清不掉脏键（污染相邻测试）。
- 跑全量测试前**先停 dev 后端**：`flash.stream.auto-poll=true` 的开发进程会和集成测试抢 Stream 消息，异步用例随机少 1 条，不是代码 flaky。
- 密钥口令走 `.env`（spring-dotenv，进程工作目录自动读），**别写死在 application.yaml**；`.env` 不入 Git。
- 前端 user/order id 全程字符串透传，别 `Number()`——Long id 超 JS 安全整数 2^53，一转换就失真、接口全 404。
- 本机 Maven：用 `./mvnw`（wrapper 自带发行版）；用户级 `MAVEN_HOME` 已损坏勿引用。
- 集成测试清理要全：三类 Redis 键（`rate:limit:*` / `seckill:user:*` / stream 键 / rank / metric）+ 用例写过的 DB 行。
