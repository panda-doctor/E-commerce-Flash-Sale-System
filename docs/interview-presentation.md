## 一、项目概述与业务背景（1 分钟）

### 1.1 业务场景

电商大促秒杀：一个活动放出 1000 件商品，5 秒内涌入上万请求，业务约束有三条硬要求：

| 约束 | 含义 | 一旦违反的后果 |
|---|---|---|
| **不超卖** | 卖出数量 ≤ 库存 | 超卖要赔付、客诉 |
| **不丢单** | 抢到的用户必须有单 | 用户投诉"抢到了没订单" |
| **不重复** | 一人一场一单 | 黄牛刷单、库存被单点薅空 |

同时系统必须**活着**——不能因为瞬时流量把数据库打挂。

### 1.2 一句话架构

> **"同步链路只做 Redis，订单最终落 MySQL。"**

同步阶段（用户能感知的、必须毫秒级返回的部分）只做四件事：限流 → 校验 → 原子扣减 → 入队。**任何一步都不写数据库**。数据库只承载异步的、匀速的订单落库。这就是**削峰**的本质：把"每秒上万次写库"摊平成"每秒十几次写库"。

### 1.3 分层结构（口述时按这个顺序讲，不要跳）

```
前端 SPA（Vue 3 + Vite）
        │  HTTP / JSON（统一 Result<T> 响应）
        ▼
Controller 层      接口入口 · 令牌鉴权 · 参数校验
        ▼
Service 层         秒杀主链编排 · 缓存编排 · 榜单 · 指标
        ▼
   ┌────────────┴────────────┐
   ▼                         ▼
Redis 7（热路径）         MySQL 8（冷终态）
缓存 / 库存 / 令牌 /         商品 / 活动 / 订单 /
限流 / Stream / 榜单 /       消息日志 / 指标快照
指标                          （5 张表）
```

**关键句**："Redis 承担**热路径**——所有高并发读写都落在 Redis；MySQL 承担**冷终态**——只存最终结果和配置。这条分界线是整个架构设计的起点，后面所有技术选型都是围绕它做的。"

## 二、秒杀主链路设计（3 分钟，这是讲解的核心骨架）

### 2.1 完整链路（口述时配合手绘或用这张图）

```
POST /api/seckill/execute
   │
   │ ① 滑动窗口限流        ZSet      rate:limit:{activityId}:{userId}
   │        超限 → 42900
   ▼
   │ ② 活动缓存校验        Hash      seckill:activity:{activityId}
   │        未开始/已结束/已取消 → 各自语义码
   ▼
   │ ③ Lua 原子执行        ┌─────────────────────────────┐
   │                       │ SET NX 令牌（防重）           │
   │   单脚本内原子完成     │ GET + 判断库存                │
   │   seckill_execute.lua │ DECRBY 扣减                   │
   │                       │ 失败则 DEL 令牌回滚           │
   │                       └─────────────────────────────┘
   │        返回 -2 → 40901 重复  返回 -1 → 40902 售罄
   ▼
   │ ④ 生成订单号 → XADD    Stream   seckill:order:stream
   │        入队失败 → 反向补偿（库存 +1、令牌 DEL）
   ▼
   │ ⑤ 立即返回             { result: "QUEUED", orderNo }
   ▼
═══════ 以下为异步，用户已经拿到响应 ═══════
   │ ⑥ 消费者组拉取         XREADGROUP，150ms 一次
   │ ⑦ 幂等落库             INSERT seckill_order（唯一键兜底）
   │ ⑧ 落库成功 → XACK
   │ ⑨ 落库成功 → ZADD NX 入榜   ZSet  seckill:rank:{activityId}
```

### 2.2 为什么是这个顺序（面试官最常追问的点）

**① 限流为什么放最前面？**
"限流是 ZSet 的 `ZREMRANGEBYSCORE` + `ZCARD`，O(logN) 纯内存操作，不查库、不回源，是整个链路里**最便宜的一步**。把它放最前，能以最低成本挡掉刷子。
反过来，如果限流放在扣减之后，被限流的请求就已经消耗了库存和令牌——错误码也会变成 40901 而不是 42900，语义就错了。"

**② 为什么查活动走缓存而不是查库？**
"秒杀活动信息是**读多写极少**的典型数据，而且预热后整个活动期间不变。预热时把活动配置写进 Redis Hash，`execute` 全程不碰数据库——这是一条设计红线，主链打库就等于把数据库暴露在瞬时流量下。"

**③ 为什么扣减和防重必须在一个脚本里？**
"这是踩过坑之后的结论。早期版本是服务层分两步：先 `setIfAbsent` 建令牌，再执行扣减脚本。中间有几毫秒的空隙，会出现两类不一致：
- 扣减失败但令牌已建 → 用户明明没抢到，却被锁 30 分钟不能重试；
- 服务在两步之间崩溃 → 令牌残留、库存悬空。

把「建令牌 → 校验库存 → 扣减 → 失败回滚」合并成一个 Lua 脚本后，这四步**同生共死**，中间态被彻底消除。"

**④ 为什么先扣库存再发消息，不是先发消息？**
"顺序不能反。**消息是"我已拥有库存"的凭证**——只有扣减成功了，这条消息才有意义。如果先发消息再扣减，扣减失败时消息已经进队列，消费者会凭空建出一张没有库存支撑的订单。
另外，`XADD` 失败时我做了**反向补偿**：库存 `INCR` 回补、令牌 `DEL` 删除。否则库存扣了、订单没有、用户重试还被判重复——三个问题叠在一起。"

### 2.3 一条消息的四条命运路径（讲可靠性时的核心图）

```
XADD 投递成功
   │
   ├─ 路径①  正常        消费 → 幂等落库(CREATED) → ZADD NX 入榜 → 日志 SUCCESS → XACK
   ├─ 路径②  可恢复失败  retry_count+1、置 FAILED、**不 ACK 留 PEL** → 5s 后重试重新拾起
   ├─ 路径③  超阈值      retry_count ≥ 3 → XADD 死信流 → 日志 DEAD → ACK 原消息
   │                      └─ 若订单未落库 → **补偿库存与令牌**（避免资源永久悬空）
   └─ 路径④  人工回放    管理端按原消息 ID 从死信流找回 → **重新原子占位** → 重投主 Stream → XDEL 死信
```

**这段的讲解价值**：它把"消息不丢、不重复、可兜底"从口号变成了可验证的实现。面试官听到"四条路径全覆盖"就知道不是背概念。

### 3.1 后端框架与数据访问

| 技术 | 角色定位 | 功能职责 | 解决什么问题 · 怎么落地 |
|---|---|---|---|
| **Java 17** | 语言基座 | 提供 Record、Switch 表达式、模式匹配等特性 | 用 Switch 表达式写图片魔数校验（`AbstractImageStorage`），比 if-else 链清晰且编译器保证穷尽 |
| **Spring Boot 3.3.4** | 应用容器与自动装配 | IoC 依赖注入、内嵌 Tomcat、自动配置、`@Scheduled` 调度 | 秒杀链路所有组件通过构造器注入组装（`@RequiredArgsConstructor`）；消费者调度器用 `@Scheduled` 驱动 |
| **Spring MVC** | Web 层 | REST 接口、拦截器、全局异常处理 | 见 3.2 与 3.5：拦截器做鉴权、`@RestControllerAdvice` 做统一异常收敛 |
| **MyBatis-Plus 3.5.7** | ORM 框架 | 单表 CRUD、`LambdaQueryWrapper` 条件构造、乐观锁插件、自动填充 | ① `LambdaQueryWrapper` 用方法引用写条件，编译期校验字段名，避免字段改名后 SQL 静默失效；② `@Version` + `OptimisticLockerInnerInterceptor` 实现活动配置更新的乐观锁；③ 全局 `id-type: INPUT`，**ID 由应用生成而非数据库自增**（见 3.6） |
| **MySQL 8.0** | 持久化终态存储 | 商品/活动配置、订单终态、消息日志、指标快照 | 5 张表；**正确性靠唯一键兜底**：`uk_activity_user(activity_id, user_id)` 保证一人一单，`uk_order_no` 保证消息级幂等，`uk_stream_message` 保证一条消息一条日志。这是整个幂等体系的**最后一道防线**——即使 Redis 数据被清空或绕过，数据库也不允许出现重复订单 |
| **HikariCP** | 数据库连接池 | 连接复用、超时控制 | `maximum-pool-size=20`。**参数依据**：秒杀主链不查库（热路径在 Redis），数据库只承担异步落库，20 连接足够；`connection-timeout=10s` 快速失败优于无限阻塞 |
| **Spring Boot Validation** | 参数校验 | `@Valid` + JSR-303 注解 | DTO 层用 `@NotNull/@Min` 拦截非法入参；**服务层再做一次兜底校验**（防内部调用绕过 Controller），形成双层防护 |
| **Lombok** | 样板代码消除 | `@Data/@Builder/@RequiredArgsConstructor/@Slf4j` | 编译器期生成 getter/setter/builder，让源码聚焦业务逻辑 |
| **Maven** | 构建与依赖管理 | 依赖管理、打包、测试执行 | `spring-boot-starter-parent` 统一版本管理，避免依赖冲突 |

### 3.2 Redis 相关（项目技术含量最高的部分）

| 技术 | 角色定位 | 功能职责 | 解决什么问题 · 怎么落地 |
|---|---|---|---|
| **Redis 7.0** | **热路径唯一数据源** | 缓存、库存、令牌、限流、消息队列、榜单、指标 | 整个同步链路的读写全部落在这一个内存实例上，数据库被彻底隔离在异步侧。使用 **database 1**（与默认 db0 隔离，排查时须 `redis-cli -n 1`） |
| **RedisTemplate + Lettuce** | Redis 客户端 | 命令封装、连接池管理 | 自定义序列化策略（见下）；Lettuce 基于 Netty 异步 + 连接共享，池配置 `max-active=16 / max-wait=2s` 防止线程无限阻塞 |
| **Jackson 序列化 + DefaultTyping** | 值序列化器 | 对象 ↔ JSON 双向转换 | 用含 `JavaTimeModule` 的 ObjectMapper 支持 `LocalDateTime`；开启 DefaultTyping 让反序列化能还原具体类型。**安全加固**：DefaultTyping 必须配 `BasicPolymorphicTypeValidator` **白名单**（只放行本项目实体包 + `java.time/util/lang/math/net`），替换掉放任一切的 `LaissezFaireSubTypeValidator`——否则 Redis 数据一旦被污染，可通过 JSON 里的 `@class` 字段引导实例化任意 gadget 类（RCE 风险） |
| **Redisson 3.34.0** | 分布式锁 | 可重入锁、看门狗续期、等待队列 | 守护**写入口**：活动预热、库存重置、商品缓存击穿回源。**关键设计决策：秒杀主链不加锁**——防重和扣减已由单条 Lua 原子完成，加分布式锁会把"Redis 单线程原子"降级成"锁排队"，纯负优化 |
| **Lua 脚本** | **原子性载体** | 把多条命令打包成一次原子执行 | 三个脚本：`seckill_execute.lua`（防重+扣减+回滚）、`rate_limit.lua`（滑动窗口）、`decr_stock.lua`。原理：Redis 命令处理是**单线程**的，脚本以整段为一次"命令"执行，期间不被其他客户端命令穿插 |
| **Redis Stream** | 消息队列 | 生产者投递、消费者组拉取、ACK、PEL、死信 | 削峰的核心载体。选它而不是 List 的原因：**List 的 `BRPOP` 没有 ACK 机制**，弹出即丢失、无法重试；Stream 有完整的**消费者组 + PEL（Pending Entries List）+ XACK** 语义，具备"至少一次投递"能力 |
| **ZSet** | 有序集合 | 按 score 排序、范围查询、去重 | **两处关键用法**：① 滑动窗口限流的成员集合（score = 请求时间戳，按时间范围清理）；② 实时排行榜（member = userId，score = 抢单时刻，`ZADD NX` 天然幂等） |
| **Hash** | 字段映射 | 部分字段读写、`HINCRBY` 计数 | 活动信息缓存（一次 `HGETALL` 取全部字段）、指标计数（三类拒绝次数） |

#### 3.2.1 完整的 Redis 键设计（讲解时可以画出来，体现"键即契约"）

| 键模式 | 类型 | 业务语义 | TTL 设计 |
|---|---|---|---|
| `product:detail:{productId}` | String | 商品详情缓存 | 300 + random(0~60) 秒（**防雪崩抖动**） |
| `seckill:activity:{activityId}` | Hash | 活动配置 + 时间窗 | 活动结束时间 + 60s 缓冲 |
| `seckill:stock:{activityId}` | String | **实时库存**（原子扣减对象） | 同上 |
| `seckill:user:{activityId}:{userId}` | String | **幂等令牌**（存在即已抢） | 1800 秒（30 分钟） |
| `rate:limit:{activityId}:{userId}` | ZSet | 滑动窗口请求记录 | window + 1 秒 |
| `seckill:order:stream` | Stream | 订单消息队列 | 无（业务侧治理） |
| `seckill:order:dead:stream` | Stream | 死信队列 | 无（人工回放后 XDEL） |
| `seckill:rank:{activityId}` | ZSet | 实时手速榜 | 无（复盘需要） |
| `seckill:metric:{activityId}` | Hash | 三类拒绝计数 | 无 |
| `seckill:lock:{用途}:{id}` | 分布式锁 | Redisson 锁 | leaseTime 30s |

**加分句**："所有键前缀都收敛在 `CacheKeyConstant` 常量类里统一管理。这不是洁癖——我在项目里**真的踩过三次键前缀拼错的坑**：比如把库存键错拼成活动 Hash 的前缀，对 Hash 类型执行 `GET` 直接报 `WRONGTYPE`。集中管理之后这类事故从根上消失了。"

### 3.3 图片存储

| 技术 | 角色定位 | 功能职责 | 解决什么问题 · 怎么落地 |
|---|---|---|---|
| **策略模式 + `@ConditionalOnProperty`** | 存储抽象 | 本地磁盘 / 阿里云 OSS 双实现热切换 | 业务代码只依赖 `ImageStorageService` 接口，不感知底层。`aliyun.oss.enabled=true` 走 OSS，`false`（默认）走本地磁盘。**切换只改配置、不动代码** |
| **阿里云 OSS SDK 3.17.4** | 对象存储 | 图片上传、URL 回显 | `OssImageStorageService` 上传至 bucket 并返回 `{domain}/uploads/{yyyyMM}/uuid.ext`，域名可替换为 CDN |
| **Spring 静态资源映射** | 本地存储兜底 | `/uploads/**` → 本地目录 | `FileStorageWebConfig` 把上传目录映射为静态资源路径，本地模式零依赖可用 |

**安全设计（面试常问）**：校验逻辑抽在抽象基类 `AbstractImageStorage`，三重防线——
① 扩展名白名单 + 5MB 上限；
② **文件头魔数校验**（PNG/JPG/GIF/BMP/WebP）——MIME 类型是客户端可伪造的，必须看真实字节；
③ 文件名由服务端 UUID 重写，防路径穿越。
**这里有个我特意做的改进**：最初要求"扩展名必须与文件头一致"，结果微信/网页另存的图片扩展名常与实际格式不符（`.png` 实际是 JPEG），合法图片被误拒。改成**魔数优先**：内容验证是白名单图片就收，按真实格式命名存储；伪装成图片的脚本依然被拒——安全不降级，收益是零误伤。

### 3.4 外部集成（AI 能力）

| 技术 | 角色定位 | 功能职责 | 解决什么问题 · 怎么落地 |
|---|---|---|---|
| **OpenAI 兼容协议客户端** | LLM 接入层 | 调用 Chat Completions | 自研 `OpenAiCompatibleChatClient implements LlmChatClient`，用 Spring 6 的 `RestClient` 实现。**接口抽象**意味着换模型供应商（DeepSeek / 通义 / 豆包）只需换实现类。协议：`POST {base-url}/chat/completions`，取 `choices[0].message.content` |
| **`RestClient` + 懒加载单例** | HTTP 客户端 | 连接与读写超时控制 | 客户端懒构建 + `synchronized` 双重检查，可并发重复执行且幂等；拆成独立方法而非 `@PostConstruct`，**便于单元测试直接 new 而不依赖 Spring 容器** |
| **grounding 防幻觉设计** | 提示词工程 | 用真实业务数据约束模型输出 | **核心设计**：不用重型 RAG（秒杀商城"知识"就是商品+活动目录，量级很小），而是**每次请求实时查库组装事实目录注入 system prompt**，限定模型只基于真实数据作答、查无则如实说明。目录查询失败自动降级为空目录，不阻塞对话主链路 |
| **数据口径一致性** | 横切设计 | 保证 AI 与接口口径同源 | 目录中的活动状态**不信任 DB 的 status 快照**，按当前时间窗口实时推导"未开始/进行中/已结束"——与 `execute` 接口的校验口径完全同源。这解决了一个真实的坑：曾出现"AI 把已过期活动当还有场次"，靠目录过滤 + 实时推导根治 |
| **成本与稳定性护栏** | 资源控制 | 控制 token 开销、容错 | 目录上限 30 行、历史最近 10 轮、单条截断 600 字；空回复自动重试 1 次（部分模型对复杂场景偶发返回空串，不能把空串当成功）；无状态会话，历史不落库 |

**讲解价值**："这块是我主动加的差异化能力。我想说明的不是'我会调 API'，而是**我懂 LLM 应用的工程边界**——知道什么时候该上 RAG、什么时候实时查库更合适，知道怎么用 prompt 约束模型不编造，知道异常和成本要怎么兜。"

### 3.6 关键工具类设计

| 工具 | 解决的隐藏问题 |
|---|---|
| **`IdGenerator`**（分布式 ID） | ID = `((nowMs - EPOCH) << 10) | sequence`，**恒小于 2^53**。为什么必须这样设计？因为前端 JavaScript 的 `Number.MAX_SAFE_INTEGER` 就是 2^53，超过就会**静默丢精度**——早期用 `timestamp * 1_000_000`（约 1.78e18）导致活动 ID 传到前端后被取整，新建活动后详情/榜单/指标**全部 404**。这是"前后端数值边界"的经典问题，解法是让 ID 主动适配 JS 安全整数范围 |
| **`OrderNoGenerator`**（订单号） | 压测暴露过一个极隐蔽的 bug：库存归零但订单只有 999。根因是生成器**混用了两个时钟源**（一个 `System.currentTimeMillis()` 判定毫秒、一个 `LocalDateTime.now()` 拼输出文本），毫秒跨边界时序号被重置但文本相同 → 生成重复订单号 → 被 `uk_order_no` 当作幂等合并 → **静默丢单**。修复为单一时钟源 + 单毫秒溢出护栏 |
| **`RequestIdUtil`** | 生成 `yyyyMMddHHmmss + 4位序号` 的请求追踪号，写入 `Result.requestId`，让一次请求的全链路日志可串联 |

## 四、技术深挖（面试官要听的部分：为什么这样设计）

### 4.1 防超卖：为什么必须用 Lua

**问题本质**：`GET stock` 和 `DECR stock` 是两条独立命令，中间可以被其他请求穿插——这就是典型的 **check-then-act 竞态**。两个线程同时读到库存 1，都判断"有库存"，然后各扣一次，库存变成 -1，超卖。

**三种解法对比**（体现技术选型能力）：

| 方案 | 原理 | 代价 |
|---|---|---|
| 分布式锁串行化 | 加锁保证同一时刻只有一个请求 | 并发度骤降，秒杀场景不可接受 |
| `DECR` 后判断负值回补 | 先扣再查，负数就加回来 | 有中间态；回补本身可能失败 |
| **Lua 单脚本原子** | 判断与扣减合并成一次原子执行 | ✅ 本项目选择 |

**`seckill_execute.lua` 契约**（这段能背下来很加分）：

```lua
KEYS[1] = 库存键   KEYS[2] = 幂等令牌键
ARGV[1] = 令牌值   ARGV[2] = 令牌 TTL(1800s)

① EXISTS 令牌 → 存在则 return -2        （重复秒杀）
② SET 令牌 NX EX ttl → 失败 return -2   （防御性再判）
③ GET 库存 → 不存在或 ≤0 → DEL 令牌, return -1  （售罄，令牌回滚）
④ DECRBY 库存 1 → return 剩余库存        （≥0 表示成功）
```

Java 侧逐一映射返回值：`≥0 → QUEUED`、`-1 → 40902`、`-2 → 40901`、`null → 50000`。
**坑**："每个返回码都必须有明确分支——早期 `-2` 曾落进兜底的 `else` 分支，被错误地变成了系统错误 50000。测试直测脚本返回码就是为了防这个。"

**关于 Lua 的两个必须知道的边界**（主动说出来，体现深度）：
1. **原子 ≠ 事务回滚**：Lua 中途报错，已执行的写命令**不会自动回滚**。所以脚本必须写得防御性强，不能指望"出错自动回滚"。
2. **Lua 慢会阻塞整个 Redis**：Redis 命令处理是单线程的，脚本执行期间整个实例被占用。所以脚本必须短小，禁止循环大集合或复杂计算。本项目三个脚本都是 O(1)~O(logN)。

### 4.2 一人一单：四道幂等闸

为什么需要四道？因为**每一层都可能失效**，必须层层兜底：

| # | 闸门 | 防的场景 | 位置 |
|---|---|---|---|
| ① | **Lua 内 SETNX 令牌** | 同用户并发/重复点击 | `seckill_execute.lua`，与扣减同脚本原子 |
| ② | **消费者 `selectByOrderNo` 查重** | 消息重复消费 | `SeckillOrderConsumer#handle` |
| ③ | **DB 唯一键 `uk_activity_user`** | **最终兜底**——Redis 数据被清空也能挡住 | `seckill_order` 表 |
| ④ | **XACK/PEL + 榜单 `ZADD NX`** | 消息层与统计层各自幂等 | `SeckillOrderConsumer` / `SeckillRankServiceImpl` |

**幂等键为什么是 `activityId + userId` 而不是 orderNo？**
"因为业务语义是'**一个人在一个活动里只能有一单**'，所以自然键就是活动+用户，与数据库的 `uk_activity_user` **完全同构**——Redis 和 DB 两层校验口径一致。
不能用 orderNo：orderNo 是在扣减成功之后才生成的，它无法在'扣库存之前'挡住重复请求。orderNo 是**消息层的幂等键**（`uk_order_no`），两个键各管一层，职责不重叠。"

**令牌 TTL 为什么是 30 分钟？**
"令牌的语义是'**排队资格**'，不是'已购凭证'。太短——用户在异步落库完成前重复请求会二次扣库存；太长——万一消息彻底失败，用户被锁死很久。30 分钟覆盖了'入队 → 落库 → 用户轮询结果'的完整窗口。
而且**售罄时令牌必须在脚本内回滚**——否则用户'没抢到却被锁 30 分钟'，体验和语义都是错的。"

### 4.3 分布式锁：用在哪里，以及**为什么主链不用**

这是最能体现"技术判断力"的一节。

**用了三处，共同特征都是"多步读改写"**：
1. **活动预热**（`seckill:lock:preheat:{id}`）：查状态 → 写缓存 → 更新 DB 状态。三步非原子，并发会重复预热、覆盖写。
2. **库存重置**（`seckill:lock:reset:{id}`）：含"活动进行中禁止重置"的守卫——否则会把 Redis 已扣减的库存用 DB 配置库存**"复活"**。
3. **商品缓存击穿回源**：热点 key 失效瞬间，保证只有一个线程回源数据库。

**但秒杀主链 `execute` 不加锁——这是刻意的**：
"我的判断标准是：**先看这个操作能不能用一条命令或一个脚本原子完成，能就不加锁；只有跨资源、跨步骤的读改写才需要锁编排。**
`execute` 的防重和扣减已经被单条 Lua 原子完成了，如果再加分布式锁，就是把'Redis 单线程原子'降级成'分布式锁排队'——并发度下降，还多了一次加锁的网络往返。这是纯粹的负优化。"

**锁的使用细节**（体现熟练度）：
- `tryLock(waitTime, leaseTime)` 显式传 leaseTime：**一旦显式传了 leaseTime，Redisson 的看门狗续期就失效**，到点自动释放。本项目业务耗时短且可控，选这个是为了"即使进程崩溃也能自动解锁"。
- `finally` 中用 `isHeldByCurrentThread()` 判断再 `unlock()`——防止锁超时被别人拿到后，自己误删了**别人的锁**。
- `InterruptedException` 必须 `Thread.currentThread().interrupt()` **恢复中断位**再抛业务异常，否则中断信号丢失。
- **锁内双重检查**：拿到锁之后必须重新查一次状态——等锁期间可能已经有别的线程做完了。

### 4.4 削峰：Redis Stream 的完整可靠性闭环

**为什么用 Stream 而不是 List 或发布订阅？**

| 方案 | 致命缺陷 |
|---|---|
| Redis List (`BRPOP`) | **没有 ACK 机制**，弹出即从队列消失，消费失败消息就丢了 |
| 发布订阅 (Pub/Sub) | **不持久化**，没有订阅者时消息直接丢弃 |
| **Redis Stream** | ✅ 消费者组 + PEL + XACK，具备"至少一次投递"与失败重投语义 |
| Kafka | 吞吐与堆积能力更强，但需要独立集群运维——本项目 5000 请求量级 Stream 足够 |

**核心机制三件套**：
- **`XGROUP CREATE stream group MKSTREAM`**：建消费者组（`MKSTREAM` 让 stream 不存在时自动创建）。
- **`XREADGROUP GROUP g c COUNT n STREAMS stream >`**：`>` 表示只读**从未投递给本组的新消息**。
- **PEL（Pending Entries List）**：消息投递给消费者后进入 PEL，**直到 `XACK` 才移出**。读取 PEL 用 `STREAMS stream 0`——失败重试就是靠这个重新拾起未 ACK 的消息。

**"消费完成"的定义 = 业务副作用成功 + XACK**。
"这里有个我踩过的最危险的 bug：重构时 `handle` 方法丢了 `insert` 语句，变成**只 ACK 不落库**——日志显示消费成功，但订单数恒为 0。从此我审查任何消息消费代码，都会先确认'副作用语句还在不在'。"

**重试与死信（PEL 不会无限膨胀）**：
```
失败 → retry_count+1、状态 FAILED、不 ACK（消息留在 PEL）
     → 5s 后 consumerRetry 用 STREAMS stream 0 重新拾起
     → retry_count ≥ 3 → XADD 死信流 + 日志 DEAD + XACK 原消息（移出 PEL）
```

**毒消息处理（审计整改的核心）**：
"旧实现有个问题：**解析异常只打日志不 ACK**，导致坏消息每一轮都被重试、**永远留在 PEL 里**，PEL 无限增长，日志也永远进不了终态。
修复方案是把'解析失败/字段脏数据'也纳入统一失败计数——用**宽松解析**（坏字段置 null 不抛异常）重建消息和日志，再走统一的失败处理，最终同样转死信 + ACK。
兜底再兜底：如果连日志表都写不进去（基础设施故障），才保留 PEL 等待恢复。也就是'**能计数就计数，不能计数才留在 PEL**'，两条出口都有明确理由。"

**三类补偿**（资源不悬空）：

| 失败点 | 补偿动作 | 代码位置 |
|---|---|---|
| Lua 内库存不足 | `DEL` 令牌（脚本内，天然原子） | `seckill_execute.lua` |
| `XADD` 失败 | `INCR` 回补库存 + `DEL` 令牌 | `SeckillServiceImpl#compensateAfterSendFailure` |
| 进死信且订单未落库 | `INCR` + `DEL` | `SeckillOrderConsumer#compensateDeadMessage` |

**补偿的关键边界**："只补偿'**订单确实未落库**'的失败。如果订单已经落库了（比如落库成功但后续入榜失败才进死信），**绝不能补偿**——否则会把已经成交的库存误收回来。补偿动作本身必须幂等（`INCR` 一步到位、`DEL` 对不存在的键也返回成功），且失败时只记日志**不覆盖原始异常**。"

**人工回放六步**（`DeadLetterReplayService#replay`）：
1. 日志校验：必须是 DEAD 状态才允许回放
2. 找回快照：从死信流定位（**权威数据源是死信流而非日志表**——成交价快照在消费失败瞬间已随死信体写入）
3. 幂等校验：订单已落库 → 拒绝回放
4. **重新原子占位**：执行 Lua（库存 -1 + 建令牌）
5. 重投主 Stream，失败则归还占位
6. `XDEL` 清理死信

**"回放不是把旧消息塞回去，而是让用户'重新抢一次'**——先重新原子占位（库存不足/已有令牌直接拒绝），再重投。所以回放**不会造成超卖，也不会重复下单**。"

### 4.5 限流：滑动窗口 vs 固定窗口

**为什么不用固定窗口计数器？**
"固定窗口（`INCR key; EXPIRE 60`）在**窗口切换边界会突刺**：第 59 秒发 5 次、第 61 秒发 5 次，实际是 1 秒内 10 次请求，但两个窗口各自都没超限。滑动窗口按精确时间范围过滤，边界平滑。"

**`rate_limit.lua` 三步**：
```lua
① ZREMRANGEBYSCORE key -inf (now - window)   -- 清理窗口外的旧成员
② ZCARD key                                   -- 统计窗口内请求数
③ count >= maxCount → return 0                -- 拒绝
   否则 ZADD key now member + EXPIRE          -- 放行并刷新过期
```

**两个必须知道的细节**：
1. **member 必须唯一**（`时间戳-纳秒`）。如果只用时间戳，同一秒内多个请求的 member 相同，`ZADD` 会**覆盖而不是新增**，计数丢失 → 限流失效，本该被拒的请求被放行。
2. **限流键是"活动 × 用户"双维**（`rate:limit:{activityId}:{userId}`）。如果只用 userId，同一用户快速切换多个活动会**互相误伤**（抢 A 活动把 B 活动的额度用掉了）。

**顺序不能反**："限流必须在幂等之前。否则同用户的高频请求会先消耗令牌和库存、再被限流拒绝——额度白白浪费，错误码也不对（应该返回 42900，而不是 40901）。我用错误码反证过链路顺序：请求一个**不存在的活动**，也先返回 42900 而不是 404。"

### 4.6 缓存三兄弟与一致性

| 问题 | 现象 | 解法 | 代码落点 |
|---|---|---|---|
| **穿透** | 查不存在的数据，缓存永不命中，请求全打 DB | **空值标记** `""` + TTL 60s，二次查询命中标记直接返回 | `ProductCacheService#setProductEmptyToCache` |
| **击穿** | 热点 key 过期瞬间，大量并发同时回源 | **Redisson 互斥锁 + 锁内双重检查**，只有一个线程回源 | `ProductServiceImpl#getProductDetail` |
| **雪崩** | 大批 key 同时过期，流量全打 DB | **TTL 加随机抖动**（300 + random(0~60) 秒）打散失效点 | `ProductCacheService#setProductToCache` |

**空值缓存的一个精妙细节（体现踩坑深度）**：
"空值标记用 `""` 而不是 `null`——因为 Redis 存 `null` 会退化成'键不存在'，**无法与真正的未命中区分**。
读取时必须区分**三态**：① 未命中（key 不存在）→ 需要回源；② 命中空值标记（`""`）→ 数据确定不存在，直接返回 40004，**不再回源、也不删标记**；③ 命中真实值 → 反序列化返回。
我踩的坑是：早期实现写了'读到非 Product 类型就删除该键'的防御分支，结果空值标记一读就被删，**穿透保护形同虚设**。空值分支还必须禁止强转 `(Product)`，否则直接 `ClassCastException`。"

**缓存一致性策略**："采用 **Cache Aside + 更新数据库后删除缓存**，不是更新缓存。
理由：① 更新缓存在并发写下会有覆盖问题（两个线程先写 DB 后写缓存，顺序错乱导致缓存存旧值）；② 删除是幂等操作，失败可重试；③ 本项目读多写少，删除带来的"一次回源"成本完全可以接受。
**额外做了一层**：活动更新成功后不仅删缓存，还把 `preheat_status` 回置为'未预热'，要求管理员重新预热——避免'新配置 + 旧缓存'的混合态。这是审计里 R4 的整改项，**旧价旧库存落单会直接破坏资金一致性**，不是小问题。"

### 4.7 完整可靠性机制对照表（讲"不丢/不重/可兜底"时直接照读）

| 风险 | 机制 | 落点 |
|---|---|---|
| 消息丢失（消费者崩溃） | 未 ACK 的消息在 PEL，重启后 `STREAMS stream 0` 重新拾起 | `consumerRetry` |
| 消息丢失（Redis 重启） | 建组幂等（`MKSTREAM` + 沿 **cause 链**识别 `BUSYGROUP`） | `ensureGroup` |
| 重复下单 | `selectByOrderNo` 查重 + 唯一键 + `DuplicateKeyException` 兜底 | `SeckillOrderConsumer#handle` |
| 重复计分 | 榜单 `ZADD NX`（member 已存在不覆盖） | `SeckillRankServiceImpl` |
| 毒消息卡死队列 | 解析失败也计数 → 达阈值转死信 + ACK | `handleUnrecoverable` |
| 资源悬空（库存/令牌） | 三类补偿 | 见 4.4 |
| 死信无人处理 | 人工回放：先重新占位再重投 | `DeadLetterReplayService` |
| 出问题查不到 | 消息日志三态 + `retry_count` + `error_message` | `seckill_message_log` |

## 六、量化成果与工程质量

### 6.1 压测结果（JMeter 5000 请求全链路）

| 指标 | 值 |
|---|---|
| 总请求 | 5000（每用户 1 次，用户号唯一），ramp-up 90s |
| **错误率** | **0 / 5000（0%）** |
| 吞吐 | 55.5 req/s（由 ramp 速率决定） |
| 延迟 | p50 **17ms** / p90 23ms / p99 510ms |
| 成功订单落库 | **1000 = 配置库存** |
| 售罄拒绝 | 4000 |
| **守恒校验** | **1000 + 4000 = 5000（完全守恒）** |
| **Redis 剩余库存** | **0（精确归零，无超卖）** |

**压测方法论的加分表述**：
"'只有 1000 单成功'**不是失败，恰恰是正确行为**——库存 1000，成功单必须恰好 1000。判断系统健康不能看成功率，要看**守恒关系**：
- 成功订单数 **==** 库存
- 成功数 + 售罄拒绝数 **==** 总请求数
- Redis 库存 **==** 0
- DB 无重复订单号

秒杀压测的核心指标不是 QPS，而是**库存精确性**（防超卖）和**守恒**（防丢单）。"
**p99 510ms 要主动解释**："这是 ramp 期系统满负荷排队 + 单机 IO 干扰造成的尾延迟，稳态中位数只有 17ms。"

### 6.2 压测驱动修复的真实缺陷（最有说服力的素材）

**订单号并发碰撞导致静默丢单**：
- **现象**：首次压测库存归零，但 DB 订单只有 999。
- **排查过程**：先怀疑消费者丢消息 → 查 PEL 无异常、日志全部 SUCCESS → 加**守恒断言**（订单数必须等于库存）稳定复现 → 发现 `uk_order_no` 有重复订单号被幂等吞掉 → code review 定位到 `OrderNoGenerator` 的**双时钟源**问题。
- **根因**：生成器用 `System.currentTimeMillis()` 判断"是否同毫秒"，却用 `LocalDateTime.now()` 拼输出文本。毫秒跨边界瞬间两处错位，序号被重置但文本相同 → 重复订单号 → 唯一键把它当作幂等"已处理" → **库存扣了、订单没了，且完全不报错**。
- **修复**：统一为单一时钟源 + 单毫秒超限自旋等待。复测 1000/1000 无重复。
- **教训**："**唯一键 + 幂等兜底会把 ID 碰撞这种严重 bug 静默转化成丢单**。所以必须有独立的守恒断言来做监控护栏——这也是我后来坚持'压测必须断言守恒'的原因。"

### 6.3 质量保障体系

| 维度 | 内容 |
|---|---|
| **自动化测试** | 92 个用例全绿（BUILD SUCCESS），覆盖并发防超卖（200 并发抢 100，成功恰 100）、防重（同用户 50 并发仅 1 成功）、限流、消息可靠性、鉴权 |
| **代码审计** | 交付前全量逐文件审计，**38 项问题闭环**（R1~R5 高危 / C 契约 / E 边界 / F 前端 / S 安全 / M 交付），含 5 项高危：ID 精度、消息失败补偿、鉴权缺失、缓存失效、毒消息滞留 PEL |
| **回归纪律** | 每批改动跑全量测试；跑全量前**必须先停 dev 后端**（否则 `auto-poll` 的后台消费者会抢走测试写入的消息，造成"随机少一条"的假 flaky） |
| **文档沉淀** | 接口契约文档与代码对账；每个技术模式都有"问题 → 模式 → 代码位置"的索引文档 |

## 七、难点、不足与改进方向（主动暴露问题，体现自我批判）

**面试官必问"这个项目有什么不足"，诚实列举 + 给出方案，比说"没有要改的"加分得多。**

| # | 现状不足 | 改进方案 |
|---|---|---|
| 1 | ID 生成器与订单号是**单机版**（无 workerId） | 多实例部署需拆分"分片位 + 序列位"，或接入 Redis 号段 / 雪花算法 |
| 2 | 演示环境 Redis **未开持久化**，容器重启丢数据 | 生产必须开 RDB/AOF（代码里的建组幂等已是应对措施，但持久化是根治） |
| 3 | 榜单/指标/Stream 键**没有 TTL**，长期运行内存单边增长 | 加活动维度的清理任务或 TTL 策略 |
| 4 | **缺自动对账任务**（目前靠死信回放 + 人工核对） | 加定时任务双向核对：正向扫超时未完成消息、反向校验"库存 - 已售 == Redis 剩余"，偏差告警 |
| 5 | AI 客服**无 RAG、无独立限流配额** | 目录量级上来后引入向量检索；补 API 级限流与配额 |
| 6 | 注册表是**内存态**，重启失效，无上限与过期清理 | 落库 + 过期策略（演示环境是刻意的取舍） |
| 7 | **可观测性弱**——只有活动维度计数，无 Prometheus / 链路追踪 | 接入 Micrometer + Prometheus + Grafana；补齐接口级指标 |
| 8 | 集成测试**依赖本机 MySQL + Redis** | 改用 Testcontainers 提供隔离环境 |
| 9 | 消息队列与应用**耦合在 Redis 上** | 抽象 MQ 接口，便于量级上来后替换 Kafka（好消息是：**业务幂等与补偿逻辑一行都不用改**——这正是把可靠性做在业务层的价值） |

**收尾升华（这是最能打动面试官的一段）**：
"如果重新做一遍，我会把 **ID 生成多实例化**和**自动对账任务**优先补上——因为这两项直接关系到'能不能上生产'。其他的像可观测性、Testcontainers 属于工程效率范畴。
不过这个项目给我最大的收获，是三个认知的转变：
1. **正确性优先于性能**——先把一致性边界想清楚（谁是权威数据源、失败了怎么补偿），再谈优化。'落库才算抢到 + 所有失败路径都要补偿'是整个项目的主线。
2. **原子性和幂等是两件事**——Redis 提供原子性，业务提供幂等性，两者叠加才可靠，**任何单独一层都不够**。
3. **瓶颈永远在单点写**——秒杀的性能问题归根结底是库存那个 key 和数据库写入，扩容思路必须围绕'分片 + 异步化'展开，而不是无脑加机器。"

## 八、高频追问速答（准备 8 个就够）

| 追问 | 速答要点 |
|---|---|
| **Lua 为什么能防超卖？** | Redis 单线程执行脚本 → "判断+扣减"整体原子，无中间态。追问主从切换丢数据 → DB 唯一键兜底最终一致性 |
| **为什么不用 Kafka？** | 教学场景要"一站一模式"、零额外部署，Stream 的消费组/PEL/ACK 语义已完整。上量后换 Kafka（分区顺序、堆积能力更强），但**消费端的幂等与补偿逻辑不用改** |
| **消息真的不会丢吗？** | 语义是**至少一次**：ACK 前都在 PEL，进程崩溃可重读。但 Redis 无持久化时实例宕机仍会丢 → 生产要开 AOF/RDB 或换 Kafka；DB 唯一键兜住重复、对账兜住差异 |
| **重复消费怎么办？** | 四层幂等：日志终态短路（SUCCESS/DEAD 直接 ACK）、`selectByOrderNo` 查重、唯一键兜底、`ZADD NX`。重放既不重复建单也不重复计分 |
| **为什么主链不加分布式锁？** | 防重+扣减已被单条 Lua 原子完成，加锁把"Redis 单线程原子"降级成"锁排队"，纯负优化。**判断标准：能一条命令/脚本原子完成的就不加锁** |
| **缓存一致性怎么保证？** | Cache Aside + 更新 DB 后**删除**缓存（而非更新）；删除幂等可重试。项目读多写少，一次回源成本可接受。活动更新额外回置预热状态，避免"新配置+旧缓存"混合态 |
| **10 万 QPS 怎么演进？** | 按"流量漏斗 → 计算 → 存储 → 可靠性"讲：① 网关/验证码前置挡掉无效流量；② 应用无状态多实例 + 本地缓存；③ Redis Cluster 按 activityId 分片、库存分片（注意 Lua 多 key 需 hash tag 保证同 slot）；④ 换 Kafka 批量落库；⑤ 分库分表；⑥ 熔断降级 |
| **AI 那块为什么不用 RAG？** | 秒杀商城的"知识"就是商品+活动目录（量级几十条），直接实时查库注入 prompt 更准更新。RAG 的价值在**文档型大知识库**，这里引入向量库是过度设计。**目录实时查询 + 口径与接口同源**才是防幻觉的关键 |

1. 每个问题先给**结论句**（10 秒），再讲**为什么 / 怎么做**（30~60 秒），最后补**项目证据**（代码位置或测试数字）。
