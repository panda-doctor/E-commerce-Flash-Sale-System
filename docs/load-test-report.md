# 秒杀系统全链路压测报告（JMeter）

- 日期：2026-09-08
- 工具：Apache JMeter 5.6.3（CLI + Dashboard）
- 目标：`POST /api/seckill/execute` 5000 并发全链路压测
- 场景脚本：`scripts/jmeter/seckill_main.jmx`（单线程组，唯一用户 = base + threadNum）
- 环境：单机（后端与 JMeter 同机，Windows；Spring Boot :8081；Redis/MySQL 本机；自动消费 `flash.stream.auto-poll=true`）

## 一、压测场景

| 项 | 值 |
|---|---|
| 总请求数 | 5000（每用户 1 次，用户号唯一） |
| 活动库存 | 1000（预热后缓存） |
| 时间窗 | 开始时间在过去、结束时间在未来（活动开放中） |
| Ramp-up | 90s（平缓注入，避免单机客户端连接瞬时打满） |
| 预期 | 1000 成功入队 → 异步建单；4000 售罄拒绝；库存归零 |

## 二、最终结果（修复后复测：`out/run_5000_ramp2`）

### 2.1 吞吐与延迟

| 指标 | 值 |
|---|---|
| 总样本 | 5000，**错误 0（0%）** |
| 吞吐 | 55.5 req/s（由 90s ramp 决定的注入速率） |
| 平均响应 | 24 ms |
| p50 / p90 / p99 / max | 17 / 23 / 510 / 518 ms |

（p99≈510ms 为 ramp 期系统满负荷排队 + 单机 IO 干扰的最大尾延迟；稳态中位仅 17ms）

### 2.2 业务守恒与防超卖（后端权威口径）

| 项 | 值 |
|---|---|
| 成功入队并最终落库（DB `seckill_order`） | **1000 = 配置库存** |
| `seckill_message_log` 成功消息 | 1000（distinct order_no = 1000，无重复/重投） |
| 售罄拒绝（`soldOutReject`） | 4000 |
| 到达请求合计 | 5000 = 1000 + 4000（完全守恒） |
| 缓存实时库存 `seckill:stock:{id}` | **0（精确归零，无超卖）** |

**结论：5000 并发压力下，系统在任意时刻不会超卖；库存精确消耗到 0，成功订单数与库存严格相等；削峰链路（execute → Redis Stream → 自动消费 → DB 落库）全量收敛，无丢单。**

## 三、压测发现并修复的缺陷

### 3.1 订单号生成器并发碰撞（OrderNoGenerator）

**现象**：首次 20s 短 ramp 压测中，库存归零但 DB 订单只有 999；`message_log` 出现同 `order_no` 两条消息（不同 stream id）。

**根因**：`OrderNoGenerator` 用 `System.currentTimeMillis()` 判断"是否同毫秒、序号是否归零"，却用 `LocalDateTime.now()` 拼输出时间文本 —— **双时钟源在毫秒跨边界瞬间错位**：边界请求的序号在新毫秒被归零，输出文本却可能相同，产生重复订单号。`uk_order_no` 唯一键把第二个成功单当作幂等合并 → “库存 0 但订单少 1”的隐蔽丢单。

**修复**：序号判定与输出文本统一取自**同一个时钟源**（`Instant.ofEpochMilli(now).atZone(...)`），并增加单毫秒超 1 万则让出下一毫秒的护栏。

**复测**：修复后同规模压测 `订单=1000=库存`、日志 1000/1000 无重复 —— 缺陷消除。

### 3.2 首轮短 ramp 的连接类错误（非系统问题）

首轮 `20s ramp、5000 线程` 出现 345/3528 个 `HttpHostConnectException`——单机 JMeter 同时建立 5000 个短连接导致客户端端口/TIME_WAIT 打满（**后端始终 UP，已到达请求 100% 正确处理**）。改用 90s 平缓 ramp 后 5000 请求全部到达、0 错误。压测客户端注入方式需与实际并发目标匹配（见 4.3）。

## 四、评价与建议

1. **防超卖能力通过**：原子扣减 + 消息削峰在 5000 请求压力下库存精确为 0，成功单数与库存一致。
2. **异步削峰成立**：瞬时请求只消耗 Redis（Lua 扣减毫秒级），订单由消费者串行落库，DB 无瞬时冲击。
3. **幂等/可靠性健全**：DB 唯一键兜底 + 消息日志 1000/1000 无重复，无重投造成的重复单。
4. **客户端侧注意**：真实生产建议压测客户端与被压端分机，并用分布式施压（多 Agent）达到真正的万级同刻并发；本机 5000 同刻连接受 OS 端口限制。
5. **可扩展**：自动消费为单消费者串行（本机约 12+ 单/s 消化）。更高吞吐可水平增加消费者实例/组内并发（消费者组天然支持）。
