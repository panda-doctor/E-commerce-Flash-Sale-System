## 一、项目经历 · 完整条目（推荐粘贴）

### 电商秒杀系统 —— 高并发后端 × LLM 智能应用（个人独立开发）

**技术栈：** Java 17 / Spring Boot 3.3.4 / MySQL 8.0 + MyBatis-Plus / Redis 7.0 + Redisson + Lua / Redis Streams / DeepSeek LLM API / Vue 3 + Vite / JMeter

#### 项目简介

以电商秒杀"瞬时流量尖峰 + 库存强一致 + 一人一单"的典型高并发场景为载体，独立完成从"限流入口 → 缓存校验 → 原子扣减 → 队列削峰 → 异步落库"的完整秒杀链路，并在此基础上自研接入大模型，落地「小闪」AI 购物助手，打通"高并发后端 + LLM 应用"闭环。JMeter 5000 请求量级全链路压测：**错误率 0%、0 超卖、0 丢单**。

#### 后端高并发主链（核心能力）

1. **防超卖（并发扣减竞态）**：将"库存>0 判断 + DECRBY"写入单个 Lua 脚本原子执行，毫秒级完成扣减，替代易竞态的 check-then-act；DB 唯一键 `uk_activity_user` 兜住重复下单（超卖由 Lua 单点保证、不依赖 DB），压测验证库存精确归零、无超卖。
2. **缓存体系解决三大难题**：空值缓存（短 TTL 60s）防穿透；Redisson 互斥锁保证热点 Key 仅单线程回源防击穿；TTL 基础值 + 随机抖动（300+random(60)s）防雪崩；商品/活动元数据预热至 Redis，降低 DB 压力。
3. **一人一单 / 重复提交**：四道幂等闸——Lua 内 `SETNX` 幂等令牌（与扣减同脚本、原子）→ 消费者 `selectByOrderNo` 查重 → DB 唯一键 `uk_activity_user` 最终兜底 → XACK/PEL 与榜单 `ZADD NX` 保证重放不重复计分；分布式锁只守护预热/库存重置等"多步读改写"写入口，execute 主链靠 Lua 原子、不加锁（避免把单键原子操作降级为锁排队）。
4. **瞬时流量削峰 + 可靠性闭环**：同步阶段只做"限流 → 活动时间窗 → 用户去重 → Lua 扣库存"，成功即返回"排队中"；订单消息写入 Redis Stream 消费者组异步落库。可靠性做成闭环：消费失败不 ACK 留 PEL、5s 定时重试，`retry_count` 达 3 次转死信流并 ACK 原消息（毒消息不再滞留 PEL）；三类失败补偿（Lua 内售罄回滚令牌、XADD 失败回补库存+删令牌、进死信且订单未落库时补偿）；死信支持管理端人工回放——先重新原子占位再重投、成功后 XDEL，保证不超卖不重复下单；全程 `seckill_message_log` 三态（PENDING/SUCCESS/FAILED/DEAD）+ retry_count 可观测。MySQL 无瞬时冲击、订单最终一致。
5. **接口防刷**：基于 ZSet 的滑动窗口限流 Lua 脚本（`ZREMRANGEBYSCORE` 清窗口 + `ZCARD` 计数 + 唯一 member 防覆盖），按**活动 × 用户双维**限频、窗口/阈值参数化，语义码 42900 与售罄（40902）/重复（40901）区分。

#### AI 智能应用亮点（差异化）

6. **LLM 接入工程化**：自研 OpenAI 兼容 Chat Completions 客户端（RestClient，接口抽象可替换）接入 DeepSeek；API 密钥环境变量注入不入库、异常统一收敛为语义错误码（50300/50301），响应不携带内部信息。
7. **实时目录 grounding 防幻觉**：不走重型 RAG，每次请求由后端实时查 MySQL 组装"在售商品 + 秒杀活动"事实目录注入 system prompt，限定模型只基于真实数据作答、查无则如实说明，从源头约束编造；目录查询失败自动降级为空目录，不影响对话主链路。
8. **数据口径一致性**：目录中活动状态不信任 DB 状态快照，按当前时间窗口实时推导"未开始/进行中/已结束"，与秒杀 execute 接口校验口径同源，避免过期场次误导模型（曾出现"AI 把已过期活动当还有场次"，通过目录过滤 + 实时推导根治）。
9. **成本与稳定性护栏**：目录上限 30 行控制 token 消耗；无状态会话 + 历史清洗（角色归一化、单条 600 字截断、最近 10 轮窗口）；空回复自动重试一次、超时与连接参数可配、HTTP 客户端懒加载单例化。

#### 量化成果与工程质量

- **JMeter 5000 请求全链路压测**（库存 1000）：错误率 0%；p50 17ms、平均 24ms；成功订单 1000 = 配置库存、售罄拒绝 4000，请求量完全守恒 → 任意并发不超卖、不丢单、不重单。
- **压测驱动缺陷根治**：通过"库存归零但订单少 1"的数据对账，定位订单号生成器混用 `System.currentTimeMillis()` 与 `LocalDateTime.now()` 双时钟源导致的单号碰撞丢单，修复为单一时钟源 + 单毫秒溢出护栏后复测守恒。
- **工程闭环**：92 个自动化测试用例全绿（BUILD SUCCESS，覆盖并发防超卖/防重/限流/消息可靠性/鉴权）；统一 `Result<T>` 响应（requestId 可全链路追踪）；交付前全量代码审计 **38 项问题闭环**（R/C/E/F/S/M 六级，含 5 项高危：ID 精度、消息失败补偿、鉴权缺失、缓存失效、毒消息滞留 PEL）；Vue 3 可视化看板（秒杀按钮状态与后端语义码联动、AI 侧栏、排行榜、移动端适配）端到端演示。

## 四、面试追问准备（自检清单）

1. 为什么 Lua 脚本能防超卖？Redis 单线程 + 脚本整体原子执行；如果 Redis 主从切换丢数据怎么办（提示：DB 唯一索引兜底已挡最终一致性）。
2. 四道幂等闸（Lua SETNX 令牌、消费者查重、DB 唯一键、XACK/PEL + ZADD NX）各防什么问题、哪层是最后防线？为什么分布式锁**不在** execute 主链，而只护预热/库存重置？
3. Redis Stream 和 Kafka 的取舍；消费者宕机、消息重复投递怎么保证不重单？（消息日志表 + 唯一索引）
4. "实时目录注入"和 RAG 的适用边界？为什么你的场景不引入向量库？
5. 模型空回复/超时如何降级？50300/50301 场景分别怎么触发、前端怎么联动提示？
6. 压测复述：5000 是怎么注入的（90s ramp，单机客户端端口限制）、p99 510ms 出现在哪个阶段、为什么说"到达请求守恒"是权威口径。
